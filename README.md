# Vulnerability Benchmark Ops

## Overview

Vulnerability Benchmark Ops is a custom PyTorch C++/CUDA extension designed to demonstrate the complete lifecycle of secure ML systems development:

* Custom CUDA kernel implementation
* PyTorch C++ extension development
* pybind11 integration
* Memory-safety vulnerability analysis
* Vulnerability remediation
* Numerical correctness verification
* Performance benchmarking

The project implements a custom GPU-accelerated elementwise multiplication operator and provides tooling for vulnerability demonstration, testing, and validation.

# Vulnerability Description

## Original Vulnerability

The original implementation intentionally contained a stack-buffer-overflow vulnerability for educational security benchmarking.

Vulnerable pattern:

```cpp
float stack_buffer[16];

for (int64_t i = 0; i < write_limit; ++i) {
    stack_buffer[i] = 42.0f;
}
```

### Trigger Condition

```text
numel > 16
```

### Risks

* Stack corruption
* Undefined behavior
* Silent memory corruption
* Potential crashes

---

# Vulnerability Remediation

The vulnerable stack allocation was replaced with a dynamically sized container:

```cpp
std::vector<float> safety_buffer(numel, 0.0f);

for (int64_t i = 0; i < numel; ++i) {
    safety_buffer[i] = 42.0f;
}
```

### Benefits

* Eliminates out-of-bounds writes
* Supports arbitrary tensor sizes
* Preserves functionality
* Improves memory safety

# AddressSanitizer Validation

To verify the memory-safety characteristics of both the vulnerable and the patched operators, the project supports building the extension with **AddressSanitizer (ASan)** instrumentation enabled.

## 1. Build Procedure Using ASan

AddressSanitizer relies on compiler-inserted diagnostics and library preloading. To build and execute the custom extension under ASan monitoring:

```bash
# Clean up previous builds and compile the operator with ASan enabled
ASAN=1 ./scripts/build.sh
```

Because Python is the host executable executing the compiled C++ shared object, you must preload the ASan runtime library and suppress background leak detection noise before launching Python:

```bash
# Preload the matching AddressSanitizer library
export LD_PRELOAD=$(gcc -print-file-name=libasan.so)

# Suppress background leaks from PyTorch/Python interpreter startup
export ASAN_OPTIONS=detect_leaks=0

# Execute the vulnerability trigger script
python3 test_trigger.py
```

## 2. Expected ASan Crash Output

When executing the script containing the **original vulnerable implementation** (Phase 2, adversarial input with `numel = 24`), AddressSanitizer will immediately intercept the out-of-bounds stack write, print a comprehensive stack trace, and abort the process to prevent silent memory corruption or security exploitation.

## 4. How the Adversarial Input Triggers the Vulnerability

The vulnerability is directly triggered by passing a tensor that violates the static buffer assumptions:

1. **Shape Definition**: In Phase 2, `test_trigger.py` initializes an adversarial shape of `(2, 12)`, corresponding to `numel = 24`.
2. **Buffer Allocation**: Inside the C++ function `elementwise_mul`, the local variable `float stack_buffer[16]` is allocated on the host stack, reserving exactly $16 \times 4\text{ bytes} = 64\text{ bytes}$.
3. **Out-of-Bounds Write**: The C++ loop iterates up to `numel` (24 elements). When $i$ reaches `16` and beyond, the code attempts to write floating-point values into adjacent stack slots. Because standard C++ static stack buffers have no runtime boundary safety, this write overwrites neighboring registers, local variables, or the function return address.
4. **ASan Interception**: Because the compiler compiled the stack frame with redzones, the memory locations past `stack_buffer` (offset 96 to 128+) are marked as poisoned (`f3` in shadow memory). ASan detects that the program is writing into a poisoned redzone and terminates the process instantly.

## 5. How the Patched Version Eliminates the Crash

The patched version introduces structural memory safety:

1. **Heap Allocation**: The static declaration `float stack_buffer[16]` is replaced by `std::vector<float> safety_buffer(numel, 0.0f)`. This shifts the memory allocation from the CPU stack to the **heap**, allocating a buffer sized precisely to the dynamic `numel` (e.g., $24 \times 4\text{ bytes} = 96\text{ bytes}$).
2. **Strict Bounds Matching**: The write loop is bounded strictly by `numel` (`i < numel`), matching the vector's allocated capacity exactly. No out-of-bounds writes occur, and no redzones are hit.
3. **Execution Success**: Under ASan instrumentation, the check for every write index passes because the entire dynamic range is fully addressable (`00` in shadow memory). The execution successfully completes without crashes, demonstrating full protection against stack corruption.
